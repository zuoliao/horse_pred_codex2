# Point-in-Time 正確性とスナップショット設計

## 1. 目的

予測対象レースの時点で知りえなかった情報を学習・評価へ混入させないため、情報の「発生時刻」「公表時刻」「取得時刻」「適用期間」を分けて扱う。本書は設計仕様の前段となる調査結果であり、収集基盤の実装は行わない。調査日は **2026-08-30** である。

### 調査した質問

- 前日・当日のどの時点で、出馬表、馬体重、天候・馬場、変更、調教、オッズが利用可能になるか。
- JRA-VAN の履歴、速報、SNAP、時系列オッズで「当時見えていた版」をどこまで再現できるか。
- 初回セットアップの長期履歴と、今後実時間で保存する履歴の保証水準をどう区別すべきか。
- 訂正、同日結果、相手の後続成績、現在マスタ、最終オッズによるリーケージをどう防ぐか。
- 再現可能な prediction timestamp、as-of join、監査メタデータとテストは何か。

## 2. 結論要約

### 事実

- JRA-VAN は定期配信に加え、発表日時付きの馬体重、天候・馬場状態変更、取消・除外、騎手変更、発走時刻変更、コース変更、オッズを提供する。
- 馬体重は概ね発走 1 時間前、時系列オッズは概ね 5～10 分間隔で配信される。
- 木曜出馬表発表時点の競走馬・騎手・調教師・馬主・生産者スナップショットは 2004 年以降存在するが、オンライン保持保証は 1 年である。
- 初回セットアップで取得する過去レコードは長期履歴を与える一方、後日訂正前の「当時見えていた版」を常に復元できるとは公式仕様から確認できない。

### 解釈

- 通常の `race_date` 比較だけでは不十分である。対象時点より後に公表された同日変更、後日訂正、同日後続レース、相手馬の将来成績、最終オッズが漏れる。
- 長期履歴から作る初期バックテストは、多くの項目で「最新既知データから再構築した event-time 正確な履歴」であり、「当時配信された版をそのまま再現した transaction-time 正確な履歴」ではない。
- 真に厳密な PIT 評価の品質は、今後の継続スナップショット保存で向上する。過去期間の限界は隠さず評価結果に付記する。

### 推奨

- 少なくとも「前日予測」と「当日締切前予測」を別プロダクトとして定義する。
- すべての as-of join は `published_at <= prediction_time` とし、同率時刻の扱いを固定する。未来側の最近傍値を選ばない。
- 原文を追記専用で保存し、訂正で上書きしない。`event_time`, `published_at`, `ingested_at`, `valid_from`, `valid_to` を区別する。
- オッズは予測特徴から分離し、同じ意思決定 cutoff 以前の最新値だけを市場比較・ベット判定に用いる。

## 3. 時刻の定義

| 時刻 | 意味 | 例 | PIT 判定での役割 |
|---|---|---|---|
| `event_time` | 現実の事象が起きた時刻 | レース発走、調教実施 | 過去事象かを判定 |
| `published_at` | 利用者が公式に知りうるようになった時刻 | 馬体重発表、騎手変更発表、オッズ発表 | **主要な可用性 cutoff** |
| `source_effective_at` | データが対象へ効力を持つ時刻 | 転厩発効、コース変更適用 | 版の適用判定 |
| `ingested_at` | 当方が実際に受信・保存した時刻 | JV-Link 取得完了 | ライブ運用と配信遅延の監査 |
| `valid_from/to` | 同一キーのある版が有効な期間 | 天候「晴」から「曇」への変更 | as-of join |
| `scheduled_start` | その版で予定された発走時刻 | 15:40 | 予測 cutoff の基準候補 |
| `actual_start` | 実際の発走時刻 | 15:43 | 結果情報。事前には未知 |
| `finalized_at` | 結果・払戻が確定した時刻 | レース後確定 | ラベル可用性 |

`event_time` と `published_at` が同じとは限らない。調教は実施後に配信され、結果は発走後に確定し、訂正は数日後に公表されうる。歴史データに `published_at` がない場合、都合よく `event_time` と同一と仮定しない。

## 4. 予測時点の提案

### 4.1 前日版 `T_prevday`

#### 定義案

各レースについて、公式の馬番確定出馬表を取得した後、開催前日の固定時刻でスナップショットを閉じる。正確な固定時刻は実配信ログを観測後に決める。仕様上の前日出馬表配信は概ね 12:00 頃であるため、暫定候補は **開催前日 18:00 JST** とする。

#### 使用可能

- cutoff までに公表された出馬表、枠・馬番、斤量、騎手、取消・変更。
- cutoff より前に確定・公表された全過去レース、調教、関係者集計。
- 事前に既知のレース条件、予定コース・距離・発走時刻。

#### 使用不可

- 開催当日の馬体重、天候、馬場状態、当日変更、当日オッズ。
- cutoff 後の調教/コメント/訂正。
- 結果レコードに記録された最終天候・馬場を、前日状態として使うこと。

### 4.2 当日版 `T_close`

#### 定義案

意思決定・発注余裕を確保した固定 cutoff として、暫定的に **その版の予定発走時刻 10 分前**を候補とする。T-10 は JRA の公式締切保証ではなく、評価を再現可能にする研究上の仮定である。実際の購入導線、締切、配信遅延を確認後に T-15/T-10 等を事前登録する。

#### 使用可能

- `published_at <= T_close` の馬体重、天候、馬場、取消・除外、騎手/コース/発走変更。
- `odds_announced_at <= T_close` の最新オッズ。ただし市場比較・ベット判定専用。
- cutoff より前に公表された過去成績、調教、関係者統計。

#### 使用不可

- T-10 より後のオッズ、変更、実発走情報、結果。
- 予定発走変更を後から知って cutoff を恣意的に移動し、当初は見えなかった情報を追加すること。

#### 発走時刻変更ルール案

スナップショット作成時点で公表済みの `scheduled_start_version` から cutoff を算出し、その cutoff に達したら閉じる。閉じた後の発走延期で再スナップショットを作る場合は、最初の版と別の意思決定版として保存し、バックテストで選択規則を事前固定する。

## 6. ソース別 PIT 能力

### 6.1 JRA-VAN/JV-Link

#### 事実

- 速報レコードは発表時刻を持つため、当日状態の as-of 再生に使える。
- 時系列オッズは発表時刻を持つ。取得保証は 1 年で、全式別ではなく単勝・複勝・枠連・馬連である。
- 木曜時点スナップショット（SNAP/SNPN）は 2004 年以降で、出馬表発表時点の競走馬・騎手・調教師・馬主・生産者情報を保持する。公式仕様上のオンライン保持保証は 1 年である。
- 定期データ、速報データ、セットアップデータには取得可能期間が異なる。

#### 解釈

- JRA-VAN は候補中で最も PIT 構築に適するが、「1986 年から完全な当時版」があるわけではない。
- SNAP は木曜時点を補強するが、任意時点の完全な版管理ではない。2004 年前のスナップショットは提供されない。
- 今後取り込むレコードは transaction-time PIT を構築できる。初回セットアップの古いデータは event-time 再構築として品質ラベルを分ける。

### 6.2 JRA Web、netkeiba、JBIS

#### 事実

- 各サイトは最新の出馬表・成績・基本情報等を閲覧でき、更新時刻の概略を示す場合がある。
- 今回確認した公式資料には、任意の過去時点スナップショットを一括取得する仕様、訂正前版の保持保証、研究用のオッズ時系列 API はない。

#### 解釈

- 現在表示を保存して過去 PIT とみなすことはできない。
- 利用条件の問題に加え、再現性の面でも主履歴源に適さない。

### 6.3 JRDB

#### 事実

- 曜日・時刻ごとのファイルがあり、データ仕様は配信単位を説明する。
- 週次マスタに同週土曜結果が日曜値へ含まれない等、集計ごとの基準時点が明示される例がある。
- 過去配信版をどの期間取得できるか、訂正前版を保持するかは、現行公式ページだけでは確定できない。

#### 解釈

- 配信ファイル名だけで可用時点を推測せず、各項目の定義と実取得時刻を記録する。
- 独自指数の計算入力と更新時点を確認できない場合、一次モデルの PIT 特徴から除外する。

## 7. 履歴再構築の保証レベル

データセットには次の PIT 品質を付与する。

| レベル | 定義 | 用途 |
|---|---|---|
| `PIT-A observed` | 当方が原文を実時間受信し、`published_at` と `ingested_at`、全版を保持 | 最も厳密な本番相当評価 |
| `PIT-B source snapshot` | 公式の時点スナップショット/時系列レコードを後日取得し、発表時刻がある | source-time replay。受信・処理・購入可能性は未証明 |
| `PIT-C event reconstruction` | 最新既知の履歴から、事象日・発走順で過去のみ再構成 | 長期モデル学習・予備評価 |
| `PIT-D current-master inferred` | 現在マスタ値しかなく、当時値を仮定 | 原則特徴から除外、感度分析のみ |

主要指標は PIT レベル別に報告する。PIT-C で高 ROI が出ても市場優位性の確証としない。PIT-Bでsource-time整合性、PIT-Aで受信・処理を含むoperational/shadow再現性を段階的に確認する。

## 8. バイテンポラルな記録原則

将来の実装仕様には、最低限次の概念を要求する。

| 列/概念 | 必須理由 |
|---|---|
| `source_record_type` | RA/SE/WH/WE/AV/JC/TC/CC/odds 等を識別 |
| `natural_key` | 同一対象の版を結ぶ |
| `payload_hash` | 同一内容の重複と訂正を区別 |
| `event_time` | 現実の事象順を定義 |
| `published_at` | 利用可能性を定義 |
| `ingested_at` | 受信遅延と実運用を監査 |
| `valid_from`, `valid_to` | その版の有効期間を表す |
| `source_version` | JVData/コード表の版を追跡 |
| `is_correction`, `supersedes` | 後日訂正を上書きせず連結 |
| `pit_quality` | A～D の保証レベル |

原文は append-only とし、特徴テーブルは再生成物とする。現在値テーブルを持つ場合も、それを履歴の唯一の保存先にしない。

## 9. as-of join の規則

対象レース `r`、出走馬 `h`、予測時刻 `T` について、特徴は以下を満たす版から作る。

```text
record.entity_id matches h or relevant entity
record.published_at <= T
record.valid_from <= T
record.valid_to is null or T < record.valid_to
record is not superseded by another version published at or before T
```

### 境界規則

- 同時刻は公式タイムスタンプ精度が十分なら `<=` とする。ただし分単位しかない場合、同分の順序が不明なら安全側に除外する。
- `published_at` 不明のレコードは、データ種別ごとの保守的な availability lag を適用するか、PIT-C/D として分離する。
- 「cutoff に最も近い」結合ではなく、「cutoff 以下で最大」を使う。未来の値を nearest join しない。
- タイムゾーンは保存時 UTC と元の JST を両方追跡し、競馬日付を UTC 日付に変換してずらさない。
- レース集合の相対特徴は、cutoff 時点の出走状態で全馬を再計算する。

## 10. オッズの PIT

### 事実

- 時系列オッズは 5～10 分間隔が目安であり、指定した秒の値が存在するとは限らない。
- 保証期間は 1 年である。単勝以外の全式別を同じ長期時系列として利用できない。

### 推奨ルール

1. 各レース・式別について `announced_at <= decision_cutoff` の最新スナップショットを選ぶ。
2. `odds_age_seconds = decision_cutoff - announced_at` を必ず保存し、許容する最大陳腐化時間を事前登録する。
3. スナップショットがないレースは最終オッズで補完せず、PIT バックテスト対象外または欠損とする。
4. 予測確率とオッズを同一 `decision_snapshot_id` に結び、別時点の確率/オッズを混ぜない。
5. 払戻と確定オッズは結果側に保存し、損益計算以外では入力から遮断する。
6. 最終オッズを使う診断は `final-odds oracle diagnostic` と明記し、現実的ベット結果と分ける。

### 不確実性

- JRA の実際の発売締切、ネット投票の受付、JV-Link 配信遅延を含め、T-10 で確実に発注可能かは本調査だけでは検証していない。
- 1 年より前の時系列取得は公式に保証されない。長期 ROI 検証の前提にしない。

## 11. 履歴集計で起きやすいリーケージ

### 11.1 現在マスタの使用

現在の騎手・調教師通算成績、現所属、現クラス、現獲得賞金を過去レースへ結合すると未来情報になる。過去確定レースを `published_at < T` で走査して独自に集計する。木曜 SNAP は時点照合に使えるが 2004 年以降・保持保証 1 年という限界がある。

### 11.2 同日・同開催の結果

対象レースより前に終了した同日レースの結果は理論上利用可能だが、歴史セットアップには「何時に確定配信されたか」がない場合がある。初期の長期再構築では、次のいずれかを事前固定する。

- 保守的方式：対象開催日の開始前までに確定した履歴だけを使い、同日結果を全て除外する。
- 実時間方式：PIT-A/B 期間に限り、`finalized/published_at < T` の前レース結果を含める。

長期 PIT-C で結果の発走順だけから同日利用可能性を仮定しない。土曜結果が日曜にどう反映されるかも、提供元マスタに依存せずイベント履歴から定義する。

### 11.3 相手の将来成績

過去レースのレベルを「そのレースに出た馬の最終生涯成績」で評価すると未来漏洩になる。各過去レース直前に凍結した rating を使う。対象レース時点までに判明した相手の後続成績を使う別設計は、予測時には可用でも、過去パフォーマンスの意味を後知恵で更新するため、基本特徴と分離して仮説検証する。

### 11.4 調教師・騎手・種牡馬集計

暦年最終成績、シーズン最終順位、後年の産駒成績を過去年へコピーしない。各対象レース時点の累積と複数窓をイベント履歴から計算する。観測数の少ない値は縮約するが、縮約の全体平均も学習期間内だけで推定する。

### 11.5 前処理とカテゴリ辞書

- 欠損補完、標準化、target/frequency encoding、特徴選択、キャリブレーションは train 期間だけで fit する。
- カテゴリの出現頻度を全期間で数えない。
- LightGBM の early stopping やハイパーパラメータ調整に final holdout を使わない。
- race 内正規化自体は同じ予測時点の全出走馬情報なら可能だが、取消後の出走集合ルールを固定する。

### 11.6 コース・制度の遡及正規化

現在のクラス名やコース属性を過去へ機械的に当てはめると、意味の変化を隠す。原コード、適用期間、正規化版を保持し、2001 年の馬齢表記変更、クラス制度変更、競馬場改修等を有効日付きマッピングとして扱う。

### 11.7 訂正データ

後日訂正を過去の予測入力へ遡及適用すると transaction-time leakage になる。ただし、初回セットアップでは訂正前版が得られない場合がある。

- PIT-A/B：`published_at <= T` の当時版を使う。
- PIT-C：最新訂正済み値を使ったことを明記し、結果ラベルの正しさと当時可視性を区別する。
- 重大訂正を発見したら、訂正あり/なし双方の感度を報告する。

## 12. 分割とデータセット生成への要求

### 推奨

- 時間順に train / development / final holdout を分け、境界を固定する。
- 特徴は各行の `prediction_time` を引数に再現可能に生成する。
- データセット manifest にソース版、取得日時範囲、PIT 品質比率、cutoff ルール、オッズ鮮度、欠損率、訂正件数を記録する。
- 同一レースの馬行は必ず同じ split に置く。
- 評価はレース単位で集約し、同一レースの一部を train、一部を test に分けない。
- final holdout は一度固定後、反復調整に使わない。PIT-A データが十分蓄積した時点で、別の前向き検証期間を予約する。

## 13. PIT 監査テスト案

本調査では実装しないが、後続仕様に最低限含めるべき検査である。

| テスト | 合格条件 |
|---|---|
| future publication | 全入力の `published_at <= prediction_time` |
| result isolation | 対象レースの確定着順・タイム・払戻が特徴表にない |
| odds isolation | 一次モデル特徴に odds/popularity/vote-count がない |
| as-of monotonicity | cutoff を早めたとき、後発表レコードが現れない |
| correction replay | 訂正前 cutoff は旧版、訂正後 cutoff は新版 |
| entity history | 騎手/調教師/血統集計の最大イベント時刻が cutoff 未満 |
| opponent freeze | 過去レース相手 rating が当時版に固定 |
| same-day policy | PIT レベル別の同日結果ルールに違反しない |
| odds staleness | オッズ時刻が cutoff 以下、age が非負 |
| split integrity | 同一レースは一つの期間にのみ存在 |
| reproducibility | 同 manifest から同 fingerprint を生成 |

## 14. 既知の限界と追加調査

- 実 JV-Link データをまだ監査しておらず、各速報のタイムスタンプ精度、訂正レコードの実挙動、欠損時のコードは仕様書確認段階である。
- 過去の exact `published_at` がないレコードについて、保守的ラグを何時に設定するかは実データ調査が必要である。
- 前日固定時刻 18:00 と T-10 は研究上の提案で、ユーザーの実運用と公式投票締切を確認して決定する。
- 予定発走延期時に再判断を許すか、初回 cutoff で固定するかはベット運用仕様で選ぶ。
- 時系列オッズの実取得最古日と欠測率を、契約後に式別・年別・開催別に監査する。
- 初期履歴の「最新訂正済み版」による PIT-C バイアスを、将来蓄積する PIT-A 期間で定量比較する。
